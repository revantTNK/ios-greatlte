# Galaxy S8 (SM-G950F / SM-G950N, dreamlte) port — progress

This file is the active handoff for the Galaxy S8 port (repo `galaxios8`, branch `main`; the original work
lives in `Floppikrob/ios-galaxy-s8`). It ports the A5XELTE work (iOS 16.7 on a Galaxy A5 2016 with
4 KiB pages, Cortex-A53, GICv2, Samsung S-Boot) to the Galaxy S8, Exynos 8895.
Observations on the phone and build results are kept apart from plans.

## Hardware facts measured on the phone (2026-10-20)

Read from TWRP (`/proc/cpuinfo`, `/proc/iomem`, `/sys/firmware/fdt`) and with
the bare-metal `s8-probe` (v2–v7) booted from BOOT:

- S-Boot enters the BOOT "kernel" at **EL1, MMU off**, x0 = DTB (`0x8A000000`),
  Image loaded around `0x800b4000`. **CNTFRQ_EL0 = 0**; the DT timer is 26 MHz.
- Boot CPU: Cortex-A53 **MPIDR 0x100**, ID_AA64MMFR0 `0x1122` (no 16 KiB
  granule), ID_AA64ISAR0 `0x11120` (no LSE). TWRP's Linux 4.4 contains the
  arm64 CPU-feature sanity check and reports no variation for the Mongoose
  cores, so no S8 core has 16 KiB pages or LSE atomics.
- GIC-400: GICD `0x10201000`, GICC `0x10202000`; virtual timer PPI 11 (INTID 27).
- PSCI 0.1 IDs (`cpu_on 0xc4000003`). From the probe, CPU_ON returns 0 but no
  secondary core ever executed the probe's entry — unsolved; start with `cpus=1`.
- Display: S-Boot framebuffer `0xcc000000`, 1440×2960 XRGB8888 (bootargs
  `s3cfb.bootloaderfb`). The panel is in command mode; writes only reach it
  after unmasking the DECON trigger: `0x1281` → `0x12860070` (as uniLoader).
- RAM: `80000000-bc7fffff`, `c0000000-ffffffff`, `880000000-8ffffffff`. The
  high 2 GiB bank has no firmware carve-outs; XNU gets it (ADT dram-base/size).
- TWRP ramoops: base `0x92000000`, 2 MiB, ecc 0, console zone `0x92080000`
  (512 KiB). Text written there in pstore format survives a forced reboot (with
  a few bit flips) and appears in `/sys/fs/pstore/console-ramoops-0`.
- Storage is UFS (BOOT `sda7`, USERDATA `sda24`, 57 GB); no S8 driver yet.

## Build pieces

- `xnu/patches/0124-dreamlte-s8.patch` (generated by
  `tools/dreamlte/apply-dreamlte.py`): S8 framebuffer/marker/boot-MPIDR macros
  in `A5XELTE.h`, used by the early console, the AppleCLCD bridge and SweetCPU;
  A5 GPIO keys off by default. The MACHINE_CONFIG stays `A5XELTE`.
- Several A5 patches were zero-context, had a stray `xnu/` prefix or wrong hunk
  counts, so `git apply` (the CI path) skipped them. They were regenerated with
  context from a locally replayed tree (`tools/dreamlte/prep-xnu-tree.sh`,
  `export-patches.sh`); `verify-ci-apply.sh` confirms that plain `git apply`
  now yields the same tree (only the staged-HFS 0031/0041 need CI staging).
- `shim/dreamlte/`: S-Boot loader. Copies the `SWEETXNU` payload from the BOOT
  ramdisk into the high bank, writes boot_args and jumps to XNU. Logs to screen
  and pstore, leaving an 8-byte slot at `0x920ff000` for XNU's entry marker.
- `tools/mkadt_dreamlte.py`: S8 ADT (iPhone X D22AP identity and /product).
- `tools/dreamlte_mkboot.py`: Samsung BOOT packer (stock header + DTBH);
  byte-identical when repacking the stock kernel and ramdisk.

## Boots 19-31 (2026-10-20/21)

Taken from the commit messages of the upstream author; boot numbers are theirs.
Observations are on the phone unless marked as a guess.

- **SMP.** Boot 19 (loader probe): `CPU_ON` alone never starts a core; after
  `CPUn_CONFIGURATION |= 0xF` (as Samsung's `exynos-pmu.c`) the A53 at MPIDR
  0x101 started. Boot 20: kernel still lacked the 0 -> 0xF power edge, so it
  now power-cycles the core around `CPU_ON`. Boot 21: still no core; the
  firmware keeps the `CPU_ON` entry in a 32-bit PMU INFORM register, so a
  low trampoline (`ldr/br` at `0x8f000000`) is passed instead of the >4 GiB
  XNU entry. Boot 22: 4/4 A53 cores up.
- **Keys.** Power GPA2-4, volume up GPA0-3, volume down GPA0-4, Bixby GPA0-6
  (as Home), ALIVE pinctrl `0x164b0000`. DAT offsets were wrong until
  boot 22 (GPA0 `0x020`, GPA2 `0x060`, DAT `+4`); boot 24: all four reach HID.
- **4-core stall.** Boots 22-24: rendering stalled because timed wakeups
  failed off the boot CPU (CoreAnimation's `dispatch_apply` waiting for
  workqueue threads). Samsung's DT marks the arch timer `use-physical-timer`,
  so DREAMLTE uses `CNTP_*`, PPI 14 (INTID 30). Boot 25: stall gone.
- **Touch.** S6SY761 (`sec,sec_ts`) on USI09 HSI2C `0x108e0000`, IRQ gpa1-0.
  Boot 25: every transfer timed out (SDA held low) because S-Boot leaves
  S2MPS17 LDO34 (1.85 V) / LDO35 (3.0 V) off; `pmic.c` enables them over
  SPEEDY. Boot 26: boot status 0x20, id 0xac3761, firmware ok. Kernel driver
  polls the interrupt line from a thread. Boot 27: 77 touches reached
  SpringBoard.
- **Clock.** The loader decodes the S2MPS17 RTC and appends `s8rtc=`; boot 27:
  launchd logged the real date.
- **Battery.** MAX77865 on `hsi2c_32` (USI13): fuel gauge `0x36`, charger
  `0x69`; 3000 mAh. Boot 29: 99 %, 4149 mV.
- **Display.** Boot 27-28: the 1125x2436 presentation stalled while the ADT
  still announced a 1440x2960 canvas; the canvas now follows the presented
  size. DECON_F/IDMA0 scan `0xcc000000` with the DPU SYSMMUs off. Boot 28:
  moving the IDMA base with only a DECON global update changed nothing on
  screen. Boot 29 (`sweetfb_hz=30`): heavy artifacts; copy moved to SwapEnd.
  Boot 30: back to full-screen 1440x2960, without `a5fb_keep_on` so locking
  blanks the panel. Boot 31 (video): lock screen, home screen, App Library,
  Control Center work, but frames tear; each copy now starts right after a
  DECON frame-done (**not yet tested on the phone**).
- **Mongoose cluster.** `mngs_probe` follows Samsung's
  `pmucal_cpu_exynos8895.h` (`cluster0_on`, `cpu00_on`). Boot 31: cluster and
  core 0x000 status 0xf, `CPU_ON` rc 0, core never ran the entry. The probe
  now repeats the A53 order (power off, `CPU_ON`, power 0 -> 0xF + DD0,
  `CPU_ON`). **Not yet tested.**

## Mongoose cluster: root cause found (2026-10-22, boots m1-m8)

Loader experiment build `LOADER_CFLAGS=-DMNGS_DIAG=1` (smp_probe.c
`mngs_diag`, `psci_early`): results go to the boot-args (`mngs=`) and to pmsg;
the loader then resets straight into TWRP (INFORM2 0x12345678, INFORM3
0x12345674, PMU SWRESET, as Samsung's sec_reboot.c), so a test cycle needs
nobody at the phone. This TWRP's ramoops is 32 KiB at 0x92000000 with the
pmsg zone at 0x92004000 (the upstream TWRP used 2 MiB, pmsg 0x92180000); the
loader now writes both.

- m2/m3/m5/m6 (PMU only): the Mongoose cluster sequencer stayed at 0x60000,
  NONCPU/L2 off although their configurations already read on (0xf000f /
  0x7); `cluster0_on`, NONCPU/L2 writes and 0 -> on edges changed nothing. A
  core edge powered core 0x000 (status 0xf) but it never ran. S2MPS17 BUCK2
  (vdd_cpucl0) is on (ctrl 0x78, ~675 mV), so not the rail.
- m7 (E1): plain PSCI CPU_ON as the first thing in the loader starts neither
  0x101 nor 0x000: the loader's probes are not the cause.
- TWRP's Samsung 4.4 kernel boots all 8 cores with plain PSCI 0.1 in 0.3 s.
  S-Boot (LUN sdb, read to the git-ignored research/sboot/) sets
  CPUn_OPTION = 0x10a for the Mongoose cores before the kernel (file offset
  0x74f1c); bit 8 = ENABLE_AUTO_WAKEUP_INT_REQ (Samsung S5E8890-syspwr.c).
- **m8 (E2): with GICD_CTLR set to 1 (S-Boot leaves it 0), plain PSCI CPU_ON
  started A53 0x101 and Mongoose 0x000; the cluster sequencer went to 1.** No
  PMU writes and no SGI were needed. The PMU powers cores and clusters on a
  GIC wake request, which needs the distributor enabled.
- Patch 0124 now: DREAMLTE SweetCPU sets GICD_CTLR bit 0 and does a single
  CPU_ON through the low trampoline (no PMU power edge); new boot-arg
  `s8autoreset=N` resets the kernel into TWRP N s after the UFS log starts
  (after a log flush), for unattended kernel test cycles.
- **K1** (CI run 39704628589, kernel SHA-256 `1b47c372...7b37b`, loader
  without the old `mngs_probe`, `cpus=4 s8autoreset=180`): `4/4 CPUs
  initialized`, each A53 started by one CPU_ON through the trampoline;
  GICD_CTLR already read 0x1 (XNU's GIC driver had enabled it), so the PMU
  power edge was never needed, only the trampoline. `hfs: mounted`,
  SpringBoard, then `S8 AUTORESET` and the phone was back in TWRP after about
  4 minutes, unattended.
- **K2** (same kernel, `cpus=8 s8autoreset=180`, flashed 08:29): the phone
  did not come back to TWRP within 8 minutes, so the kernel stopped before
  the UFS log thread could run the reset (most likely a panic, which halts
  with `debug=0xc`, or a hang while starting a Mongoose core). Needs the
  screen and a TWRP log pull. The SweetCPU topology check already expects
  MPIDR 0x0-0x3 for logical 4-7.

## K2 analysis (static, 2026-10-22)

Read in the patched tree (prep-xnu-tree.sh + 0124, Lima VM):
- **Cause of K2: SweetCPU's IOKit personality matched only
  `'arm,cortex-a53'`.** The ADT names logical 4-7 `samsung,mongoose-m2`
  (`tools/mkadt_dreamlte.py`), so those nubs got no driver,
  `sweet_cpus_registered` stayed at 4, and `SweetCPU::startAll` panicked
  "CPU registration timeout" after 10 s, before any Mongoose CPU_ON. With
  `debug=0xc` and no `PE_halt_restart` the phone just stopped. 0124 now
  matches `('arm,cortex-a53', 'samsung,mongoose-m2')`.
- Checked and fine for MPIDR 0x0-0x3: `reset_vector` looks the CPU up by
  MPIDR Aff1:Aff0 (`and x0, x15, #0xFFFF`), so 0x000 finds logical 4;
  topology maps MPIDR Aff1 to logical clusters (A53 0, Mongoose 1); the GICv2
  code reads each core's own ITARGETSR0 to address SGIs, so the Mongoose GIC
  interfaces 0-3 are handled; the SweetCPU topology check expects 0x0-0x3 for
  logical 4-7. Cosmetic: `getCPUName` says "Cortex-A53" for every core.
- Still unverified until it runs: Mongoose ID registers (CTR_EL0, DCZID_EL0,
  ID_AA64MMFR0) against the A53's; TWRP's Linux reported no CPU feature
  variation, so they are expected to match.

### CPU clocks (2026-10-23)

Read in TWRP (debugfs, Samsung's 4.4 source `exynos8895/android_kernel_samsung_universal8895`):

- ECT ASV: this chip is group 7 for both clusters (`asv_summary` "big:7,
  LITTLE:7"). Table versions 5-8 give the voltages seen on the PMIC: Mongoose
  1469 MHz 743.75 mV and 1066 MHz 675 mV; A53 455 MHz 618.75 mV and 1053 MHz
  775 mV (BUCK2/BUCK3 V = 300 mV + 6.25 mV x code, checked against
  `regulator_summary`). Versions 5/6 and 7/8 differ only at Mongoose
  >= 2314 and A53 1690 / <= 832 MHz.
- PLLs (ECT `pll_list`): F = 26 MHz x M / (P x 2^S), P = 3; CMU_CPUCL0/1 + 0x120.
- **Samsung's Linux does not set CPU clocks itself.** `cpufreq/domain@0`
  cal-id 0x0b040003 (dvfs_cpucl1, A53, cpus 0-3) and `domain@1` 0x0b040002
  (dvfs_cpucl0, Mongoose, cpus 4-7) are ACPM vclks: `cal_dfs_set_rate` sends
  "FREQ_REQ id kHz" to the APM firmware (a Cortex-M core) over the mailbox,
  and the firmware sets the BUCK from its own ASV table, then the PLL. No
  init message is needed (Linux only copies the fvmap from SRAM).
  Mailbox 0x16440000 (INTGR0 0x08, INTCR1 0x20, INTSR1 0x28), SRAM 0x16500000
  (0xb400), initdata at +0x2850, DVFS channel 5 (TWRP DT `acpm_ipc`,
  `acpm_dvfs`). Queue layout: `acpm_ipc.c`, `fw_header/framework.h`.
- TMU: block 0x10080000 (early TMU, started by the bootloader). Sensor s:
  code at 0x40 (+4 per three sensors from sensor 2, 9 bits each), trim at
  4 x s, two-point 25/85 C. Mongoose sensors 0, 2-5 (balance), A53 sensor 1.
  Samsung throttles from 83 C (passive), hot 115 C. TWRP idle: 37 C.

## Note 8 (greatlte) touch (2026-10-23)

The user's second phone is a Galaxy Note 8 (Exynos, `greatlte`, SM-N950F/N).
Buttons, charging indicator and the display path come up with the S8 images;
touch does not. Hardware source: Samsung's `android_kernel_samsung_universal8895`
(`tw90-android`, `arch/arm64/boot/dts/exynos/exynos8895-greatlte_common.dtsi`).

- **The touch controller is a different chip family.** The S8 node uses
  `sec,sec_ts` with the S6SY761 ("y761") and the mainline-style protocol this
  port already speaks. The Note 8 node is also `sec,sec_ts` at `0x48`, but
  Samsung binds it with `drivers/input/touchscreen/sec_ts_y661`, project
  `"GREAT", "N950"`, firmware `tsp_sec/y661_great.fw`, `afe_base 0x117`,
  `max_coords 4095 4095`. Everything around it is the same:
  hsi2c_23/USI09 `0x108e0000`, IRQ gpa1-0, S2MPS17 LDO34 `tsp_io` 1.85 V and
  LDO35 `tsp_avdd` **3.3 V** (the S8 DT says 3.0 V; commit 053ae52 already
  raised the loader to 3.3 V).
- **Protocol comparison (read, not guessed).** `sec_ts.h` from the two
  drivers: same command numbers for `SENSE_ON 0x10`, `SET_TOUCHFUNCTION 0x30`,
  `READ_FW_INTEGRITY 0x21`, `READ_DEVICE_ID 0x22` (5 bytes), `READ_PANEL_INFO
  0x23`, `READ_ID 0x52` (3 bytes), `READ_BOOT_STATUS 0x55` (0x20 = app,
  0x10 = boot), `READ_ONE_EVENT 0x60` / `READ_ALL_EVENT 0x61` (8-byte events,
  same bit fields), `READ_TS_STATUS 0xAF`. Differences that matter:
  `SW_RESET` is **0x42** on y661 and 0x12 on y761, and the default function
  bits are `TOUCH|PALM|WET = 0x61` (both families). So a y661 should answer
  this driver; the S8's own log line ("id ac3761", status 0x20) is just its
  ID read through 0x52.
- **Loader (`shim/dreamlte/touch_probe.c`)** now probes both: boot status,
  `0x52`, `0x22`, `0x23`, `0x21`, `0xaf`, current `0x30`, IRQ level; soft
  resets with 0x42 and 0x12 when not in app mode; drains the queue until the
  boot-complete INFO event; writes function 0x61 and `SENSE_ON`; then polls
  `0x60` for `s8tsprobe=N` seconds (default 4, max 60) whether or not the IRQ
  line asserts, and counts reads/events. `s8tsreset=1` power-cycles LDO34/35
  first (state after S-Boot may matter). `s8tspause=N` holds the loader
  screen N seconds so the output can be photographed.
- **Kernel (`tools/dreamlte/dreamlte_touch.c`, patch 0124)** no longer returns
  when the boot status is not 0x20: it soft-resets (0x42 then 0x12), reads and
  logs `0x52`/`0x22`/`0xaf`/`0x21`, waits for the boot-complete event, writes
  function 0x61 + `SENSE_ON` with the old retries, and logs the IRQ level.
  New boot args: `s8tspoll=1` ignores the IRQ line and reads the queue
  unconditionally (for a wrong or never-asserting IRQ pin), `s8tsdebug=N`
  prints the first N raw 8-byte events. The S8 path is unchanged apart from
  the function byte 0x01 -> 0x61, which is what Samsung's y761 driver sends.
- Regenerated `xnu/patches/0124-dreamlte-s8.patch` from
  `tools/dreamlte/prep-xnu-tree.sh` (xnu-8796.141.3 + the A5 patches) +
  `apply-dreamlte.py`; `git apply --check` passes on that tree. CI run IDs and
  the phone result are to be filled in after the next test.
- **Not tested on a phone.** No Note 8 was attached while this was written.
  Images built locally with the *old* kernel (loader diagnostics only):
  `shim/dreamlte/out/s8-tsdiag-boot.img` (SHA-256 `6d20d112...b23fdc`,
  `s8tsprobe=20 s8tspause=30`, same boot args as the user's `s8-ios-boot.img`)
  and `s8-tsdiag-reset-boot.img` (SHA-256 `4af66ece...a9961`, same plus
  `s8tsreset=1 s8tspoll=1`). The loader ends with a one-line
  `TS SUMMARY: boot=.. id52=.. id22=.. events=..` for a photo. Flashing BOOT

- What the probe should answer, in order: (1) does `0x55`/`0x52` return at
  all (IC powered, bus and pins right); (2) app mode or boot mode after the
  resets; (3) does the boot-complete event appear; (4) are there coordinate
  events while a finger is on the panel, and does gpa1-0 follow them. A `0x52`
  value that is not `ac3761` would confirm the y661.
